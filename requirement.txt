백엔드 API 요구사항 (프론트엔드가 기대하는 스펙)
=================================================

이 문서는 프론트엔드(src/api.js)가 실제로 호출하는 API와, 각 API가 가정하고 있는
요청/응답 형식을 정리한 것입니다. 백엔드를 구현하거나 붙일 때 이 스펙에 맞추거나,
스펙이 다르다면 src/api.js 쪽을 함께 수정해야 합니다.

공통
----
- Base URL: 환경변수 VITE_API_BASE_URL (.env 파일, 기본값 http://localhost:8000)
- 요청 Content-Type: application/json
- 프론트와 백엔드가 다른 origin(포트 포함)이면 백엔드에서 CORS 허용 필요
  (Access-Control-Allow-Origin, Access-Control-Allow-Methods: POST,
   Access-Control-Allow-Headers: Content-Type, Authorization)


1) POST /api/auth/login
------------------------
설명: 이메일/비밀번호 로그인

요청 바디:
  { "email": string, "password": string }

성공 응답 (200):
  { "token": string, "user": { "name": string, "email": string } }

실패 응답 (401 등):
  { "message": string }

프론트 동작:
  - 성공 시 token은 localStorage(authToken), user는 localStorage(authUser)에 저장되어
    새로고침해도 로그인 상태가 유지됩니다.
  - token은 이후 모든 /api/chat/stream 요청에 Authorization: Bearer <token> 헤더로
    자동 첨부됩니다.


2) POST /api/chat/stream
--------------------------
설명: 메시지를 보내고 LLM 응답을 스트리밍(SSE 형식)으로 받음

요청 헤더:
  Authorization: Bearer <token>   (로그인한 경우에만 첨부. 비로그인 상태에서도
                                    호출은 가능하며, 이 경우 헤더가 없습니다.)
  Last-Event-ID: <id>             (재연결 시도일 때만 첨부. 아래 "재연결" 참고)

요청 바디:
  {
    "messages": [ { "role": "user" | "assistant", "content": string }, ... ],
    "persona": string | null
  }
  - messages는 이 대화(스레드)에서 지금까지 오간 메시지 전체 + 이번에 새로 보낸
    사용자 메시지까지 포함한 배열입니다(가장 오래된 것부터 순서대로).
    새 대화의 첫 메시지라면 배열에 user 메시지 1개만 들어있습니다.
  - 백엔드는 이 배열을 문맥으로 사용해 답변해야 합니다(이전 턴을 무시하고
    마지막 메시지에만 답하면 안 됩니다).

정상 응답 (200):
  Content-Type: text/event-stream
  "field: value" 줄이 이어지는 형식이며, 한 줄이 하나의 이벤트로 즉시 처리됩니다
  (블록 사이 빈 줄은 없어도 됩니다):

    data: {"delta": "안녕"}
    data: {"delta": "하세요"}
    data: [DONE]

  - data: 줄의 JSON에 delta 필드가 있으면 텍스트 조각으로 이어붙입니다.
  - data: [DONE] 을 받으면 정상 종료로 간주합니다.
  - data: 줄이 유효한 JSON이 아니면(delta 필드 없는 JSON 포함) 오류로 처리하고
    스트림을 중단합니다 — 잘못된 형식의 텍스트를 답변인 것처럼 보여주지 않습니다.
  - 각 "data:" 줄은 개행(\n)으로 끝나는 것을 권장하지만, 스트림이 개행 없이
    끊겨도 프론트가 마지막 줄을 마저 처리합니다.

  event: 필드 (선택):
    event: error 다음에 오는 data: 줄은 델타가 아니라 오류로 처리됩니다:
      event: error
      data: {"message": "요청이 처리 중 실패했습니다."}
    event: 필드가 없거나 다른 값이면 기본값(message, 델타)으로 처리합니다.

  id: / retry: 필드 (선택, 재연결용):
    id: <문자열>   — 마지막으로 받은 이벤트 ID로 기억해뒀다가, 재연결 시
                     Last-Event-ID 요청 헤더로 다시 보냅니다.
    retry: <ms>    — 스트림이 [DONE]/오류 없이 갑자기 끊겼을 때, 이 값을
                     밀리초로 해석해 그만큼 기다린 후 같은 요청을 최대 2번까지
                     재시도합니다. retry: 필드를 보낸 적이 없다면 재연결을
                     시도하지 않고 그대로 종료 처리합니다.

오류 응답 (4xx/5xx, 스트리밍 시작 전):
  { "message": string }   — 없으면 응답 바디 원문을, 그마저 없으면 상태 코드만
  표시합니다.


변경 이력
--------
- 이 문서는 새로운 API를 추가하거나 기존 API의 요청/응답 형식을 바꿀 때마다
  함께 갱신합니다.
- SSE 파싱을 event:/id:/retry: 필드 인식 + 재연결 + JSON 파싱 실패 시 오류
  처리로 강화 (src/api.js).
- /api/chat/stream 요청 바디를 message(단일 문자열) -> messages(대화 전체
  배열)로 변경. 멀티턴(이어서 대화하기) 지원을 위해 프론트가 스레드의 전체
  메시지 기록을 함께 보내도록 바뀌었습니다 (src/App.jsx, src/api.js).
