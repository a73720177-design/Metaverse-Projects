사용법: 아래 항목마다 **위치 → 기존 문장 → 바꿀 문장** 순서로 적었다. HWP에서 기존 문장을 찾아 그대로 바꿔 넣으면 된다.

- `【시연 확인】`은 시연한 팀원이 화면이나 로그에서 값을 확인해 채워야 하는 칸이다.

## 1. 요약 (전체 교체)

**기존:** "본 논문은 발표자료를 근거로 … 설치 재현성은 후속 평가 과제이다."

**바꿀 문장:**

> 본 논문은 발표자료를 근거로 평가자 페르소나별 예상 질문과 후속 대화를 제공하는 LLM 기반 발표 준비 지원 시스템을 제안한다. PDF·PPTX·DOCX에서 추출한 발표자료와 평가자별 참고자료를 구분하여 생성에 결합하고, 벡터 검색과 어휘 검색 결과를 순위 융합하여 근거 구간을 선택한다. 생성 결과에는 페르소나 특성의 원문 인용 검증과, 근거 ID·고유 용어·수치·중복을 차례로 점검하는 질문 필터를 적용하여 자료에 없는 내용을 전제한 질문을 줄이도록 하였다. 전체 기능은 Windows 실행파일로 개인 PC에 설치되어 로컬에서 동작한다. 시연에서는 Qwen3.5-4B(4비트 양자화, vLLM)로 세 평가자 페르소나의 예상 질문을 생성하여, 같은 발표자료에서 평가 관점에 따라 서로 다른 근거를 인용한 질문이 제시됨을 확인하였다.

**이유:**

- 기존 요약은 한계("후속 평가 과제")로 끝나서 아무것도 확인하지 않은 인상을 준다.
- 핵심 기여인 근거 검증이 요약에 없다.

**확인:** 시연 PC가 CPU(Ollama) 모드였다면 모델명을 "Qwen3 4B(Ollama)"로 바꾼다. 원고에 "vLLM의 생성 검사 통과"가 적혀 있으므로 GPU 모드였을 가능성이 높다.

## 3. I장 서론 끝 (문장 교체)

**기존:** "연구 범위는 시스템 구현과 자료 입력부터 질문 생성까지의 시연이다. 기반 모델의 재학습과 발표 역량 향상에 대한 통계적 검증은 포함하지 않는다."

**바꿀 문장:**

> 본 연구의 기여는 다음과 같다. 첫째, 발표자료와 평가자 참고자료를 구분해 결합하는 페르소나별 질문 생성 구조를 제시한다. 둘째, 생성 결과가 자료에 근거하는지 규칙으로 점검하는 근거 검증 계층을 설계한다. 셋째, 이를 개인 PC에서 동작하는 로컬 서비스로 구현한다. 모델 재학습과 교육 효과의 통계적 검증은 범위에서 제외한다.

**이유:** 심사자가 가장 먼저 찾는 "무엇이 새로운가"가 원고에 없다.

## 4. II.1 근거 검증 문단 + 표 1

**위치:** II.1 "문서와 평가자 페르소나"

**기존:** "페르소나당 1~10개의 질문을 요청할 수 있으며, 질문 형식과 수치 근거를 점검하고 유사 질문을 걸러낸다."

**바꿀 문장:**

> 페르소나당 1~10개의 질문을 요청할 수 있으며, 생성 결과에는 두 단계의 근거 검증을 적용한다. 페르소나 특성은 참고자료의 원문 인용과 함께 출력하게 하고, 인용을 NFKC 정규화·공백 제거 후 원문과 대조하여 유의미한 4자 이상이 일치할 때만 근거 있는 특성으로 채택한다. 인용이 없거나 서로 충돌하는 특성은 제외 사유와 함께 기록한다. 예상 질문은 3개씩 생성하여 표 1의 규칙을 순서대로 적용하고, 목표 개수에 못 미치면 최대 6회까지 보충 생성한다.

**표 1. 예상 질문 필터 규칙** (II.1 끝, 한 단 너비)

| 순서 | 규칙 | 기각 조건 |
|---|---|---|
| 1 | 형식 | 질문 문장이 아니거나 500자 초과 |
| 2 | 근거 ID | 근거 구간 ID가 없거나 제공 구간에 없음 |
| 3 | 고유 용어 | 근거 구간의 고유 용어·수치를 포함하지 않음 |
| 4 | 수치 | 질문의 수치가 근거 구간에 없음 |
| 5 | 중복 | 채택된 질문과 용어 Jaccard 유사도 0.82 이상 |

**공간 확보:** 같은 절의 VLM 문장 두 개("자동 모드에서는 … 달라질 수 있다.")를 아래 한 문장으로 줄인다(−4줄).

> PDF·PPTX의 시각 정보는 시각언어모델(VLM)이 사용 가능할 때 함께 처리한다.

**근거 코드:**

- `backend/app/services/persona_service.py:34,37,41`: NFKC, 공백 제거, 4자 기준
- `backend/app/models/persona.py:30`: 제외 사유
- `backend/app/services/practice_service.py:294-321`: 규칙 순서, 500자, 0.82
- `practice_service.py:337,341`: 6회, 3개
- `practice_service.py:106-121`: 수치 대조, Jaccard

## 5. II.2 검색 문장 교체

**기존:** "벡터 검색에 실패하면 어휘 기반 검색으로 전환한다."

**바꿀 문장:**

> 벡터 검색 결과는 700자 단위(중첩 100자) 청크에 대한 BM25 방식 어휘 검색 결과[3]와 RRF(k=60)[4]로 융합하며, 임베딩이 없으면 어휘 검색만 사용한다.

또한 첫 문장의 "bge-m3 임베딩" 뒤에 **[5]**를 붙인다.

**이유:**

- 기존 문장은 하이브리드 검색을 단순 대체 경로로 축소해 설명한다.

**근거 코드:**

- `backend/app/services/vector_rag.py:280-298`: 융합 호출
- `backend/app/services/rag_service.py:74-87`: RRF, 60
- `backend/app/services/rag_service.py:249-250`: 700/100

## 6. II.2 생성 모델 문장 교체

**기존:** "Qwen3의 사고·비사고 모드[2]와 별도로 서비스에서 응답을 제어한다."

**바꿀 문장:**

> 생성 모델은 CPU 모드에서 Ollama의 Qwen3 4B, GPU 모드에서 vLLM의 Qwen3.5 4B·9B 4비트 양자화(w4a16) 모델을 사용하며, 문맥 길이는 4,096 토큰이다. Qwen3 계열의 비사고 모드[2]를 사용하고 서비스에서 응답 형식을 별도로 제어한다.

**이유:**

- 화면의 선택명은 `qwen3:4b`다. 하지만 GPU 모드에서 실제로 서빙되는 모델은 `RedHatAI/Qwen3.5-4B-quantized.w4a16`이다.
- 서술과 실제 모델이 다르면 심사나 질의응답에서 문제가 된다.

**근거 코드:**

- `build/payload/setup.ps1:367-370`
- `build/payload/compose.gpu.yaml:12,25`
- `build/payload/compose.yaml:41`

## 7. II.3 배포 (두 문단 → 한 문단)

**기존:** II.3의 두 문단 전체("Metaverse-Setup.exe는 … 확인할 수 있도록 하였다.")

**바꿀 문장:**

> Windows 실행파일(Metaverse-Setup.exe)은 WSL 2·Docker 준비, DB 초기화와 모델 다운로드를 자동으로 수행한다. 서비스는 127.0.0.1에만 연결되며, DB·업로드 파일·모델은 Docker 볼륨에 저장되어 재실행 시 유지되므로 최초 설치 후에는 문서와 대화가 외부로 전송되지 않는다.

**이유:**

- 재부팅, 로그, 실행 옵션 같은 운영 세부는 학술 기여가 아니다.
- 대신 "로컬 처리로 자료가 외부로 나가지 않는다"는 의미를 드러낸다.

**확인:** "외부로 전송되지 않는다"는 최초 실행 시 모델 다운로드를 제외한 서술이다. 문장에 "최초 설치 후에는"이 들어 있으므로 그대로 써도 된다.

## 8. III장 시연 보강 (권장)

### 8-1. 장비 한 줄 (첫 문단 끝에 추가)

> 시연 PC는 【시연 확인: CPU / RAM / GPU 모델·VRAM】 환경이다.

### 8-2. 38%·34% 표현 수정 (3번째 문단)

**기존:** "학생경험책임자는 도서관 1층 38%·학생식당 34%의 낮은 분리배출률을 개선할 방법을 물어"

**바꿀 문장:**

> 학생경험책임자는 발표 대본의 기준선 가정치(도서관 1층 38%, 학생식당 34%)를 인용해 개선 방법을 물어

**이유:**

- 대본(`02_발표대본`)은 이 값을 "가정했습니다"라고 밝히고 있다.
- 원고처럼 "낮은 분리배출률"이라고 쓰면 사실처럼 읽힌다.
- 인용 수치가 자료에 있음을 보여 주는 쪽이 4번 규칙(수치)을 설명하는 데도 맞는다.

### 8-3. 표 2 (3번째 문단 뒤)

**표 2. 페르소나별 예상 질문 생성 결과**

| 페르소나 | 참고자료 | 생성/요청 | 질문 근거(요약) |
|---|---|---|---|
| 기술검토자 | 03_기술검토자 | 【시연 확인】 | 앱 설치 없이 40초 내 완료 설계 |
| 운영예산기획자 | 04_운영예산 | 【시연 확인】 | 장비 교체·추가 부품 비용 |
| 학생경험책임자 | 05_학생경험 | 【시연 확인】 | 장소별 분리배출률 가정치 |

- "생성/요청" 칸은 화면 질문 카드 수와 요청 개수다. 예: 5/5
- 생성 시간까지 확인했다면 표 아래 문장으로 추가한다. 예: "세 페르소나 질문 생성에 약 【시연 확인】초가 걸렸다."

### 8-4. 4번째 문단 압축 + 분석 구간 설명

**기존:** "각 패널에는 질문 카드와 … 후속 평가 과제로 남겼다."

**바꿀 문장:**

> 질문 생성에는 문맥 예산(기본 4,000자) 안에서 질의와 관련도가 높은 구간만 사용되어, 화면에는 전체 12개 구간 중 4~5개가 분석 범위로 표시되었다. 후속 답변 대화와 새 PC 설치 과정은 이번 시연에서 제외하였다.

**이유:**

- "4~5/12"는 원고만 읽으면 결함처럼 보인다.
- 원인이 문맥 예산 설계라는 점을 밝히면 의도된 동작이 된다.

**근거 코드:** `backend/app/config.py:88`(RAG_MAX_CONTEXT_CHARS 4000)

## 9. IV장 결론 (마지막 문장 교체)

**기존:** "동일 자료를 여러 평가 관점에서 검토하는 사용 흐름을 제시하였으며, 질문의 관련성·근거 충실도와 교육 효과, 설치 재현성은 후속 평가 과제이다."

**바꿀 문장:**

> 동일 자료에서 평가 관점별로 서로 다른 근거를 인용한 질문이 생성됨을 확인하였고, 원문 인용 검증과 규칙 기반 질문 필터로 근거 없는 생성을 구조적으로 제한하였다. 향후 필터 단계별 기각률과 질문의 근거 충실도를 정량 평가하고, 실제 발표 연습에서의 교육 효과를 검증할 계획이다.

**참고:** "필터 단계별 기각률"은 `build/payload/backend/scripts/measure_practice_filter.py`로 바로 측정할 수 있다. 측정 결과가 나오면 발표 PPT나 후속 논문에 쓴다.
