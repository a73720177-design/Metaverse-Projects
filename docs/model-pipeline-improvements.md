# 모델 호출·문서 분석·검색 개선

모델 이름, 기존 동시 생성 한도, temperature·반복 억제·추론 모드 설정은 변경하지 않았습니다. 모델은 자동 설치하지 않습니다.

## 1. 실제 요청과 같은 문맥 예산 사용

`llm-service/.env`의 `LLM_MAX_MODEL_LEN`을 모든 Ollama 텍스트 생성 요청의 `options.num_ctx`로 전달합니다. 일반 응답, 동기 스트림, 비동기 스트림에 동일하게 적용합니다. vLLM은 이 값과 `VLLM_MAX_MODEL_LEN` 중 작은 값을 앱의 한도로 사용하며, 실행 중인 서버의 한도를 자동 변경하지 않습니다.

모든 작업은 최종 프롬프트와 `/no_think` 접미사, 출력 예약분, `LLM_CONTEXT_SAFETY_TOKENS`를 함께 계산합니다. 리뷰·요약은 단일 요청이 예산을 넘으면 짧은 문서라도 map-reduce로 전환합니다. map 단계는 페이지 번호를 유지하며 큰 청크를 추가 분할하고, reduce 단계는 결과가 크면 중간 압축을 거칩니다. 예상 질문은 긴 근거 텍스트를 생략 표시와 함께 줄이고, 필요하면 참고자료부터 제외하되 실제 발표 근거와 ID를 유지합니다. 페르소나·지시사항 등 필수 입력조차 들어가지 않으면 LLM 서비스가 422로 명시적으로 거절합니다.

기본은 기존 `LLM_APPROX_CHARS_PER_TOKEN=2.0` 추정입니다. 이는 정확한 토큰 수가 아니므로 한국어·코드·수식 자료에서 여유분을 확보하고 검증해야 합니다. `LLM_TOKENIZER_PATH`에 **실제 생성 모델과 일치하는** 로컬 Hugging Face 토크나이저 디렉터리를 지정하면 토큰 단위로 계산합니다. 이 옵션은 `transformers` 설치가 필요하며 다운로드를 수행하지 않습니다. 서로 다른 모델을 함께 쓰면 공통 토크나이저가 모든 모델에 정확하다고 가정하지 마세요. 채팅 템플릿 등의 오버헤드를 위한 안전 여유는 이 경우에도 필요합니다.

## 2. 비전 모델은 문서 단위로 유지

`backend/.env`:

```dotenv
VLM_KEEP_ALIVE_SECONDS=300
VLM_UNLOAD_AFTER_DOCUMENT=true
```

페이지마다 해제하던 방식을 문서 종료 시 한 번 해제하는 방식으로 변경했습니다. 오류가 발생한 문서에서도 정리합니다. `false`로 설정하면 다음 문서에서도 재사용할 수 있도록 유한한 keep_alive 동안 유지합니다. 해제가 실패해도 성공 결과나 원래 오류를 덮어쓰지 않습니다. 기존 문서 처리 제한 시간과 단일 문서 실행 제한은 유지됩니다.

## 3. 빠른 분석과 전체 분석

`llm-service/.env`에서 기능별로 선택하고 LLM 서비스를 재시작합니다.

```dotenv
REVIEW_ANALYSIS_MODE=full
SUMMARY_ANALYSIS_MODE=full
REVIEW_FULL_MAX_MAP_CALLS=512
SUMMARY_FULL_MAX_MAP_CALLS=512
```

- 기본 `fast`: 기존 `*_MAX_MAP_CALLS` 개수로 표본 분석합니다. `coverage`와 프롬프트에 부분 분석 여부를 표시합니다.
- `full`: 모든 그룹을 분석합니다. 빠른 모드의 호출 한도를 적용하지 않습니다. 중간 결과를 계층적으로 압축하여 최종 프롬프트 한도를 지킵니다.
- `*_FULL_MAX_MAP_CALLS`를 넘으면 **모델 호출 전에 거절**합니다. 일부만 처리한 뒤 전체 분석으로 표시하지 않습니다.
- `coverage.total_chunks`는 문맥 예산에 맞춰 추가 분할된 청크를 포함합니다. 전체 입력을 분석했다는 뜻이며, 최종 요약이 모든 세부 사항을 그대로 보존한다는 보장은 아닙니다.

현재 선택은 서버 설정 단위이며 UI에 새 버튼을 추가하지 않았습니다. 기존에 저장된 요약은 캐시될 수 있으므로 설정 변경 후에는 요약 새로고침을 사용하세요. 전체 분석은 요청 수와 소요 시간이 늘어납니다. 실제 문서로 측정하고 Backend `LLM_SERVICE_TIMEOUT`, 프록시 제한, 클라이언트 대기 시간을 맞춰야 합니다. 비동기 작업 큐·중단 후 재개 기능은 포함되지 않습니다.

## 4. 선택적 로컬 검색 재정렬

BGE-M3와 DB 임베딩은 그대로 사용합니다. `RAG_MODE=vector`에서 벡터 후보를 최종 K개로 자르기 전에 유지하고, 어휘 검색과 결합한 청크를 로컬 재정렬 모델에 전달합니다. 후보는 파일별 순환 방식으로 모으고, 최종 결과도 가능한 범위에서 파일별 근거를 보존합니다. 출처 ID·페이지·파일명을 유지합니다. 임베딩 재색인은 필요하지 않습니다.

로컬 Qwen3-Reranker 서버 구현은 `llm-service/app/reranker_server.py`입니다. Ollama 생성 모델과 별개이며 yes/no 로짓으로 관련성을 계산합니다. [공식 모델 카드](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)를 참고했습니다.

선택 의존성과 모델은 별도 준비합니다. 다음은 `llm-service` 폴더에서 실행하는 예입니다. 기존 가상환경과 분리된 Python 3.11/3.12 환경을 권장하며, `python`은 그 환경의 실행 파일을 의미합니다.

```bash
python -m pip install -r requirements-reranker.txt
```

Hugging Face에서 `Qwen/Qwen3-Reranker-0.6B`의 가중치와 토크나이저를 먼저 내려받아 로컬 디렉터리에 둔 뒤 실행합니다.

```bash
python -m app.reranker_server --model /absolute/path/to/Qwen3-Reranker-0.6B --device cpu
```

GPU 환경에서는 설치한 PyTorch가 지원하는 `--device cuda` 또는 `--device mps`를 선택할 수 있습니다. 기본 입력 길이는 2048토큰이며 필요하면 `--max-length 4096` 또는 `8192`를 선택합니다. 긴 후보의 뒷부분은 이 한도에서 잘릴 수 있습니다. 서버는 루프백 주소 8003에서만 수신하며 모델 파일을 자동 다운로드하지 않습니다.

`backend/.env`를 설정하고 Backend를 재시작합니다.

```dotenv
RAG_RERANK_MODE=local
RAG_RERANK_URL=http://127.0.0.1:8003
RAG_RERANK_CANDIDATE_K=24
RAG_RERANK_TIMEOUT_SECONDS=10
```

기본값은 `off`라서 추가 설치 없이 기존 검색을 사용합니다. 서버 미실행·혼잡·타임아웃·잘못된 점수/인덱스는 경고 로그를 남기고 기존 결합 검색 결과로 돌아갑니다. CPU에서 제한 시간을 자주 넘으면 후보 수를 줄이거나 측정에 맞춰 타임아웃을 조정하세요. 재정렬 모델을 추가한다고 검색 정확도가 반드시 올라가는 것은 아니므로 실제 질문과 정답 근거로 비교해야 합니다.

## 검증 범위

자동 테스트는 모델을 대역으로 사용하여 문맥 예산, 전체 구간 전달, 단계별 압축, 페이지 간 모델 유지, 실패 시 정리, 재정렬 계약·출처·대체 동작을 검증합니다. 실제 GPU 속도, 재정렬 가중치 로딩과 한국어 정확도는 운영 환경에서 별도 비교해야 합니다.
