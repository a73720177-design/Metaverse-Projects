# RAG 검색 비용 개선

## 구현

- 채팅은 `get_for_retrieval()`로 요청한 문서의 소유권과 파일 메타데이터를 확인하고,
  문서별 키워드 후보 페이지만 조회한다. 기존 `get()`은 상세 조회·요약 등 전체 본문이
  필요한 기능에 유지한다. PostgreSQL 채팅 조회는 `documents.full_text`를 읽지 않는다.
- 후보는 영문·숫자 토큰 및 한국어 2글자 부분 일치로 찾고, 일치한 검색어 수로
  문서당 `VECTOR_RAG_CANDIDATE_K`개까지 제한한다. 기본값은 12이다.
  이후 Python BM25가 후보 페이지를 세부 청크로 나누고 순위를 계산한다.
- 인사말도 요청 문서의 권한은 검사하지만 본문 후보는 가져오지 않는다.
- 키워드 일치가 없는 문서도 메타데이터를 반환하여 벡터 검색 대상에 남긴다.
  임베딩이 없는 문서는 키워드로 검색하고, 벡터 서비스 장애 시에도 키워드로 대체한다.
- 벡터 검색은 문서별 거리순 `ORDER BY ... LIMIT`을 먼저 실행하고, 제한된 후보에만
  문서별 순위를 계산한다. 소유권, 요청 문서 범위, 모델·내용 해시 검증을 유지한다.
- 두 검색 결과는 문서 내에서 RRF(`1 / (60 + rank)`)로 합친다.
  문서 간 분량 배분은 기존 정책을 유지하며 전역 RRF로 바꾼 것은 아니다.
- BM25의 청크별 빈도·길이·문서 빈도를 LRU 청크 캐시와 함께 재사용한다.
  본문/페이지 변경 시 무효화하고, 청크 캐시 퇴출 시 함께 제거한다.

## DB 적용

`014_add_lexical_search_index.sql`은 `pg_trgm` 확장과 `lower(content)` GIN 인덱스를
추가한다. 기존 문서의 임베딩 재생성이나 저장 형식 변경은 필요 없다.
이 인덱스가 없어도 새 조회 SQL은 실행된다.

프로젝트의 기존 migration runner로 DB 연결 대상과 계획을 확인하고 적용한다.
Backend 디렉터리 기준:

```sh
python scripts/migrate_db.py --help
python scripts/migrate_db.py --database-name <DB명>
python scripts/migrate_db.py --database-name <DB명> --apply
```

`<DB명>`은 DATABASE_URL의 실제 데이터베이스 이름으로 치환한다.
마지막 명령은 모든 미적용 migration을 적용하므로 출력된 계획을 먼저 확인해야 한다.
현재 작업 환경에는 DB 연결 설정과 실행 중인 PostgreSQL/Docker가 없어 실제 DB에
migration을 적용하지 않았다. 운영 적용 시 GIN 생성 시간·잠금과 실행 계획을 확인한다.

## 검증

```sh
REPOSITORY_MODE=memory OBJECT_STORAGE_MODE=local DB_AUTO_CREATE=false python -m pytest -q
python scripts/benchmark_lexical_cache.py
```

새 회귀 테스트는 전체 본문 조회 방지, 요청 순서 유지, 권한 누락 거부,
한국어/영숫자 검색어 전달, 캐시 무효화·퇴출, RRF 중복 투표 방지를 다룬다.
`TEST_DATABASE_URL`이 있는 별도 테스트 DB에서는 실제 후보 조회의 소유권 격리,
후보 제한, 키워드 미일치 문서 유지와 벡터 검색의 격리·다양성도 검사한다.

120페이지, 168,519글자 합성 자료의 21회 반복 실험에서 BM25 특성 재계산 경로는
중앙값 34.97ms, 특성 캐시 재사용 경로는 1.72ms였다. 청크 캐시는 양쪽 모두 준비된
상태이며, DB·임베딩·LLM·콜드 스타트 시간은 포함하지 않는다. 종단 응답 속도나 실제
검색 품질의 개선 수치로 사용할 수 없다.

## 남은 검증과 한계

- 키워드 후보 제한은 정확한 전체 BM25 상위 결과를 보장하지 않는다. 실제 질문/정답
  근거 데이터로 Recall@k, 인용 정확도와 후보 수를 검증해야 한다.
- 2글자 한국어 패턴은 trigram 인덱스의 효과가 제한적이다. `LIKE ANY`의 실제 인덱스
  사용 여부도 `EXPLAIN (ANALYZE, BUFFERS)`로 확인해야 한다.
- 페이지 크기 자체에는 제한이 없어 한 페이지가 매우 길면 조회량도 커진다.
  저장 단계에서 검색 전용 청크를 분리하는 작업은 별도 스키마 설계가 필요하다.
- HNSW 사용 여부와 필터로 인한 재현율은 실제 데이터로 확인해야 한다.
  소수 문서를 검색할 때는 정확 검색이 더 유리할 수 있다.
- 업로드 임베딩은 여전히 저장 요청에서 기다린다. 작업 큐, 질문 유형별 라우팅,
  재정렬 모델, 전역 관련도 기반 분량 배분은 이번 변경에 포함하지 않았다.
- 운영 판단에는 검색 지연 p50/p95, 첫 토큰 시간, 입력 토큰 수와 실제 정답 근거
  검색률을 함께 수집해야 한다.
