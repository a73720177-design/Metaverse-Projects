# DB·RAG 점검 및 개선안 — 2026-09-16

## 결론과 확인 범위

현재 PostgreSQL + pgvector + 키워드 검색 구조를 유지하며 보강한다.
그래프 DB로 전면 전환해야 한다는 실측 근거는 아직 없다.
이번 작업 환경에는 `backend/.env`, `DATABASE_URL`, `TEST_DATABASE_URL`이
없어서 운영 DB의 연결, 실제 데이터 건수, 마이그레이션 적용 여부, 색인 완전성은
확인하지 못했다. 코드 검토 결과를 운영 DB 정상 판정으로 해석하면 안 된다.

## 적용한 수정

- 일부 문서의 색인 누락이 전체 벡터 검색을 막던 채팅 조건을 제거했다.
  기존 검색 SQL의 소유자·문서·모델·내용 해시 필터는 유지한다.
  유효한 의미 검색 결과와 전체 연결 문서의 키워드 결과를 함께 사용한다.
  결과가 없거나 검색에 실패하면 기존 키워드 검색으로 전환한다.
- 문서 상세 조회에서 청크의 본문·페이지 번호만 가져온다.
  1024차원 임베딩을 매번 전송·변환하던 비용을 줄인다.
- 문서 목록에서 전체 본문을 가져오지 않고 DB에서 길이를 계산한다.
- 소유자 범위에 문서가 없으면 파일·청크 조회 전에 반환한다.
- 읽기 전용 점검 CLI를 추가했다. 원문·비밀번호·접속 URL을 출력하지 않는다.
  이 변경에는 DB 스키마 변경이나 재색인이 필요 없다.

## 운영 점검

운영 환경의 기존 `DATABASE_URL` 설정을 사용한다. 저장된 인증정보를 문서나
명령행에 복사하지 않는다. 프로젝트 루트에서 실행:

```sh
backend/.venv/bin/python backend/scripts/audit_db.py
backend/.venv/bin/python backend/scripts/audit_db.py --owner-id <사용자-UUID>
```

스키마 계약 검사 후 파일 메타데이터 누락, 본문이 있지만 청크가 없는 문서,
빈 문서, 소유자 없는 문서, 누락·오래된 임베딩, 최대 청크 길이를 집계한다.
데이터 집계는 읽기 전용 트랜잭션에서 실행하고 쿼리 제한 시간은 30초다.
종료 코드는 정상 0, 점검 필요 또는 오류 1, 연결 설정 없음 2다.
빈 DB도 집계가 0이면 정상으로 표시되므로 `documents` 건수를 함께 확인한다.
파일 메타데이터 존재가 실제 파일 존재를 보장하지 않는다. 임베딩 서버 가용성,
실제 답변 정확도, DB의 모든 제약조건·인덱스·백업 상태까지 검사하지는 않는다.

누락·오래된 임베딩은 임베딩 서버와 모델을 확인한 후 기존 명령으로 복구할 수 있다:

```sh
backend/.venv/bin/python backend/scripts/reindex_embeddings.py --owner-id <사용자-UUID>
```

소유자 없는 데이터는 임의 사용자에게 배정하지 않는다. 파일·청크 누락은
원본 확인 후 복구한다. 위 재색인 명령은 이미 저장된 청크만 처리한다.

## 남은 구조적 과제와 다음 단계 제안 — 미구현

### 1. 검색 청크를 원본 페이지와 분리

현재 검색 시에는 700자 단위로 나누지만 저장된 임베딩은 파서 섹션(주로 페이지)
단위다. 긴 페이지를 하나의 벡터로 표현하며 임베딩 요청은 `truncate=true`다.
따라서 페이지 끝의 의미가 희석되거나 잘릴 가능성이 있다. 4000자 초과 건수는
검토용 지표이며 모델의 실제 토큰 제한을 의미하지 않는다.

제안: 원본 `document_chunks`를 보존하면서 하위 검색 청크 테이블에
원본 페이지 FK, 본문 위치, 내용 해시, 청킹 버전, 모델, 임베딩을 저장한다.
별도 색인을 채운 뒤 문서별 완전성을 검증하고 기능 플래그로 전환한다.
문서 삭제 시 검색 청크도 삭제하고, 모든 검색은 소유자와 연결 문서로 제한한다.
재색인 비용과 테이블 증가가 발생하며, 실패 시 현재 검색 경로로 되돌린다.

### 2. 속도와 검색 품질을 함께 측정

현재 벡터 SQL은 문서별 순위를 계산해 결과를 분산한다. HNSW 인덱스가 있다는
이유만으로 해당 쿼리가 인덱스를 효율적으로 사용한다고 볼 수 없다.
실데이터에서 `EXPLAIN (ANALYZE, BUFFERS)`와 p50/p95 지연을 확인한 뒤
후보 추출·재정렬 분리를 검토한다. pgvector의 인덱스 검색에는 거리 연산자를
직접 사용하는 정렬과 LIMIT 등의 조건이 있다.
[pgvector 공식 문서](https://github.com/pgvector/pgvector#querying)

평가 세트는 실제 질문 최소 30개로 구성한다: 정확한 수치·코드,
표현이 다른 의미 질문, 긴 페이지 후반 근거, 여러 문서 비교, 후속 질문,
자료에 답이 없는 질문. 정답과 원본 페이지를 지정하고 근거 적중률,
답변 정답률, 인용 정확도, 무근거 답변률, 지연·색인 비용을 비교한다.
새 경로의 도입 조건은 근거 적중률 개선, 답변·인용 정확도 비저하,
무근거 답변 증가 없음으로 잡고 허용 지연은 운영 요구에 맞춰 정한다.

### 3. GraphRAG는 관계 질문의 비교 실험 후 결정

GraphRAG는 원문에서 개체·관계를 추출하고 집단별 요약 등을 검색에 사용한다.
여러 문서의 관계나 전체 주제를 종합하는 질문을 위한 비교 후보로 적합하다.
이는 DB 제품을 바꾸기만 하면 얻어지는 기능이 아니다.
[GraphRAG 공식 설명](https://microsoft.github.io/graphrag/)
[전역 검색 설명](https://microsoft.github.io/graphrag/query/global_search/)

제안 실험: 같은 자료·질문·생성 모델로 현재 방식, 하위 청크 혼합 검색,
관계 검색 추가 방식을 비교한다. 개체 중복 통합, 관계 추출 오류,
관계별 원문 출처와 사용자 격리, 문서 변경·삭제 반영 비용도 평가한다.
관계형 데이터 저장은 PostgreSQL을 유지하고, 그래프 검색을 보조 경로로
추가하는 방안부터 검토한다. Neo4j 등 별도 DB의 필요성은 관계 탐색량과
운영 비용을 보고 결정한다.

**DB·RAG 전면 교체는 실행하지 않았다.** 교체가 필요해지면 평가 결과,
목표 구조, 데이터 이전·재색인 계획, 비용, 검증 및 롤백 방법을 포함한
기획안을 먼저 제시하고 사용자 확인 후 진행한다.
